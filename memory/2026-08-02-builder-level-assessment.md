## Operating Directives

### 1. Evidence Gate Before Architecture

For every product/commercial initiative, the sequence is:

```
Observed pain
→ Evidence packet
→ Falsifiable thesis
→ Minimum intervention
→ Customer test
→ Architecture only after signal
→ Implementation
→ Operational validation
```

**Gate:** No substantial system architecture unless at least one is true:
1. Three independent users show the same costly problem.
2. One customer is paying for resolution.
3. The system solves a documented internal bottleneck with measurable cost.
4. The work is a deliberately bounded research experiment.

### 2. One-Page Packet Required Before Building

Use `templates/one-page-initiative-packet.md` for every new initiative.

### 3. VALI Can Invalidate Commercially

VALI may return:
- TECHNICALLY_VALID
- OPERATIONALLY_VALID
- COMMERCIALLY_UNPROVEN
- CUSTOMER_REJECTED
- DISTRIBUTION_BLOCKED
- OVERBUILT
- RETIRE_RECOMMENDED

### 4. PESSI Reviews Opportunity Cost

PESSI must challenge:
- What higher-value task is displaced?
- What recurring maintenance does this create?
- Is this reversible?
- Is infrastructure proportional to demand?
- Are we automating an unvalidated process?
- Does this create another dependency on GREEN?
- Can a model-provider release commoditize the visible value?
- Is our moat in outcome, operational data, workflow integration, or merely orchestration?

### 5. Fleet Success Metrics

Measure:
- Hours of GREEN's time removed
- Revenue influenced
- Customer cycle time reduced
- Errors prevented
- Decisions made with stronger evidence
- Rework avoided
- Time from idea to external test
- % work completed without escalation
- % recommendations accepted
- % systems still used after 30 and 90 days

Do not primarily measure files produced, skills created, agents deployed, steps completed, or validation checks passed.
